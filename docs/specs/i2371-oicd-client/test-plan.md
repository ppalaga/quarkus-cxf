# Test Plan: Quarkus OIDC Client integration for SOAP clients

Spec: [spec.md](spec.md) · Issue: #2371

_AI-generated by Codex on behalf of Peter Palaga._

## Summary

Test configuration-driven OIDC acquisition, propagation, and RFC 8693 exchange on injected SOAP clients,
including token lifecycle, caller isolation, authentication failures, redirects, and WSDL retrieval.
The plan contains 26 cases: 23 P1 and 3 P2, using unit tests and Quarkus integration tests on JVM and native,
plus documentation validation and a focused prose review.
Cases with unresolved expectations identify the relevant open question instead of prescribing new behavior.

## Scope

### In scope

- Configuration under `quarkus.cxf.client."client-name".oidc`, with `disabled` as the default.
- The new `quarkus-cxf-oidc` extension, generated interfaces, and proxies injected through `@CXFClient`.
- `acquire`, `propagate`, and `exchange`, synchronous and asynchronous invocation,
  and named/default OIDC clients where applicable.
- Authenticated SOAP and REST entry points, per-invocation identity lookup, and worker dispatch.
- Token reuse, expiry, refresh, reacquisition, and exchange isolation by subject token, client, and grant parameters.
- Failures before dispatch, absence of automatic operation replay, authentication conflicts, and token masking.
- Authorization header handling on redirects, WSDL retrieval, and imported WSDL/schema documents.
- Quarkus 4.0, JVM/native execution, and documentation examples sourced from integration tests.

There is no separate Use Case Assessment section.
The original three scenarios and the Existing capabilities and design context section supply its relevant findings:
static Bearer authentication already exists, Quarkus owns token lifecycle,
CXF authorization retransmits and WSDL loading are separate paths, and async calls can move to worker threads.
No migration procedure is specified; compatibility coverage therefore concerns disabled-mode behavior,
existing authentication, and the stated Quarkus 4.0 JVM/native target.

### Out of scope

- Implementing `@OidcClientFilter`, `@AccessToken`, or OIDC support for programmatic JAX-WS clients.
- JWT-bearer exchange, mentioned only as existing Quarkus REST context; the requested exchange is RFC 8693.
- OIDC operation through other HTTP conduits, except clarifying and guarding the unsupported boundary in T-009.
- Automatic SOAP replay, an independently implemented token lifecycle/cache, or new revocation guarantees.
- Throughput benchmarks, latency budgets, accessibility checks, and unspecified migration/backport matrices.
  The spec states no measurable performance or accessibility targets.
- Exhaustive retesting of Quarkus OIDC internals, every grant type, or every identity-provider product.
- Test implementation or production-code changes during this planning task.

## Test Approach

### Existing setup and proposed placement

The repository uses JUnit Jupiter and AssertJ for runtime tests.
Deployment tests use `QuarkusExtensionTest`, ShrinkWrap archives, configuration overrides,
and exception/log assertions.
Application integration tests use `@QuarkusTest`, REST Assured, and `QuarkusTestResourceLifecycleManager`;
matching `*IT` classes extend `*Test` classes and use `@QuarkusIntegrationTest` for packaged native execution.
Surefire runs JVM tests; module `native` profiles bind Failsafe to integration-test and verify.
Awaitility, Vert.x HTTP fixtures, and certificate-generation helpers already exist.

Useful patterns include:

- [ClientAuthRedirectTest](../../../extensions/core/deployment/src/test/java/io/quarkiverse/cxf/deployment/test/ClientAuthRedirectTest.java):
  a local Vert.x server records authorization challenges and retransmissions.
- [BasicAuthTest](../../../integration-tests/client-server/src/test/java/io/quarkiverse/cxf/it/auth/basic/wsdl/BasicAuthTest.java):
  REST-driven SOAP calls and protected WSDL retrieval, with an inherited native test.
- [AsyncHandlerTest](../../../extensions/core/deployment/src/test/java/io/quarkiverse/cxf/deployment/test/client/AsyncHandlerTest.java)
  and [RestAsyncWithoutWsdl](../../../integration-tests/client-server/src/main/java/io/quarkiverse/cxf/it/vertx/async/RestAsyncWithoutWsdl.java):
  callback assertions and `CxfMutinyUtils.toUni` for calls originating on the event loop.
- [GlobalSensitiveTest](../../../extensions/core/deployment/src/test/java/io/quarkiverse/cxf/deployment/logging/GlobalSensitiveTest.java)
  and [CxfLoggingTest](../../../integration-tests/client/src/test/java/io/quarkiverse/cxf/it/logging/CxfLoggingTest.java):
  captured log records and `TestLog` access to application log files.
- `test-util-parent/test-util-internal` supplies Vert.x assertions and timeout diagnostics.
  No OIDC test resource or OIDC integration module was found in the surveyed tree.

Propose `extensions/oidc/runtime` and `extensions/oidc/deployment` following the extension split,
and a dedicated `integration-tests/oidc` application to avoid adding OIDC dependencies to unrelated examples.
These are proposed locations, not existing files or a required production-class design.
Use these path aliases in the case locations:

| Alias | Proposed directory |
|---|---|
| RT | `extensions/oidc/runtime/src/test/java/io/quarkiverse/cxf/oidc/` |
| DT | `extensions/oidc/deployment/src/test/java/io/quarkiverse/cxf/oidc/deployment/` |
| IT | `integration-tests/oidc/src/test/java/io/quarkiverse/cxf/it/oidc/` |
| APP | `integration-tests/oidc/src/main/java/io/quarkiverse/cxf/it/oidc/` |

Use unit tests for credential selection and origin comparison when those decisions are independently callable.
If they stay inside a framework-bound component, run those assertions in its smallest deployment fixture;
do not add a second implementation of the decision solely to test it.
Use deployment integration tests for CDI/configuration validation and synthetic security identities.
Use application integration tests where HTTP, authentication, token lifecycle, WSDL loading,
or thread-context propagation must work together.
A browser or separate e2e framework adds no confidence for these server-side flows.
For [R-9](spec.md#r-9), also inspect the implementation's delegation to Quarkus token lifecycle helpers;
behavioral tests alone cannot prove that lifecycle support was reused.

### CI and execution

[build.yml](../../../.github/workflows/build.yml) runs JVM jobs across its JDK/OS matrix and a native module matrix.
Both JVM and native actions also run with
`QUARKUS_CXF_DEFAULT_HTTP_CONDUIT_FACTORY=URLConnectionHTTPConduitFactory`.
Positive OIDC fixtures must explicitly select `VertxHttpClientHTTPConduitFactory` per SOAP client,
so that inherited CI defaults cannot silently remove required coverage.
Keep the unsupported-conduit configuration separate in T-009.

Register the proposed module in `integration-tests/pom.xml` and the native matrix during implementation,
and use the existing native profile and test-jar conventions.
The test-list generator discovers `integration-tests/*/pom.xml`; verify the new module appears in its output.
The docs example-copy pattern is already present in `integration-tests/client-server/pom.xml`.
No new testing framework is needed.

Future local validation must select classes, not run the whole repository test suite.
For example, after the proposed modules exist and their dependencies are installed:

```bash
mvnd -f extensions/oidc/runtime/pom.xml test -Dtest=OidcCredentialSelectionTest,OidcRedirectOriginTest
mvnd -f extensions/oidc/deployment/pom.xml test -Dtest=OidcConfigurationTest,OidcAuthenticationConflictTest
mvnd -f integration-tests/oidc/pom.xml test -Dtest=OidcAcquireTest,OidcPropagationTest,OidcExchangeTest
mvnd -f integration-tests/oidc/pom.xml verify -Pnative -Dquarkus.native.container-build \
  -Dtest=foo -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test=OidcAcquireIT,OidcPropagationIT,OidcExchangeIT
```

Select the other classes listed below for their cases and extend the native selection as specified in T-026.
Use `mvn` or `./mvnw` when `mvnd` is unavailable.
No tests need to run to produce this plan.

## Test Environment and Data

- Use the checkout's Quarkus 4.0 dependency management; the surveyed root POM selects `4.0.0.Beta1`.
  Use JDKs from the repository CI matrix and its existing native container-build setup.
- Add `quarkus-cxf-oidc`, Quarkus OIDC Client, and the inbound Quarkus OIDC security integration as needed.
  Keep real authentication in SOAP/REST ingress tests; synthetic identities belong only in focused deployment fixtures.
- Create an `OidcTestResource` under IT using the existing Vert.x/test-resource conventions.
  It supplies local token, discovery/JWKS endpoints as required by the chosen Quarkus configuration,
  a SOAP recorder, redirect listeners, and WSDL/XSD documents.
  Give fixtures dynamic ports and expose reset/observation endpoints usable by both JVM and native test drivers.
- Supply a default OIDC client and two named clients with distinguishable credentials and issued tokens.
  Include RFC 8693 clients, client-credentials clients, and intentionally incompatible grants.
  Finalize the full grant matrix through Q-1.
- Supply caller A and caller B with separate authenticated identities and access tokens,
  plus a second token for A with the same subject but a different token value.
  The token endpoint records selected client, subject token, grant type, and configured audience/scope values.
  Its issued tokens identify the fixture tuple so incorrect cache reuse is observable.
- Provide controllable `expires_in`, optional refresh tokens, OAuth errors, malformed/tokenless responses,
  connection failures, and delayed responses.
  Use Awaitility and bounded observation around configured expiry/refresh behavior instead of fixed sleeps.
  Test timeouts are harness bounds, not invented product performance targets.
- Record every SOAP POST before authentication handling, with a unique operation ID,
  received Authorization values, and an operation counter for replay detection.
  Keep recorder data out of application logs and use synthetic token values only.
- Add REST and SOAP entry points under APP that call the same injected client instances.
  Include synchronous calls, async callbacks, and an event-loop REST route using `CxfMutinyUtils.toUni`.
  Generate the service interfaces from a local WSDL with async bindings and do not add OIDC annotations to them.
- Use HTTP/HTTPS listeners and locally generated trusted certificates for origin tests.
  Change host and port separately using reachable loopback names.
  Cover scheme changes with HTTP/HTTPS listeners and isolate scheme-only comparison in T-016.
  A WSDL fixture includes valid cross-origin WSDL and XSD imports as well as redirects.
- Keep runtime WSDL loading distinct from build-time generation, using fresh client/configuration instances
  to prevent a previously loaded document from hiding a missing-credential or origin test.
- Native tests must observe the application over HTTP and its log file rather than accessing its JVM objects.
  Deployment-only synthetic credential and configuration cases remain JVM tests.

## Test Cases

All locations below are proposed new files unless explicitly described as existing.
For IT tests, add the corresponding `*IT.java` subclass for T-026.
P1 means required before merge; P2 means should have.

### Configuration and authentication modes

#### T-001: Disabled OIDC preserves existing authentication and client independence

- **Covers:** [R-1](spec.md#r-1), [R-6](spec.md#r-6); [AC-3](spec.md#ac-3); regression of existing unauthenticated,
  Basic, and static Bearer clients.
- **Level:** integration.
- **Preconditions:** Install the new extension; configure one active OIDC client alongside disabled clients.
  Use omitted mode and explicit `disabled`, with no OIDC client selected for those disabled clients.
- **Input / steps:** Invoke disabled clients anonymously, with Basic, and with configured static Bearer credentials.
  Invoke the active OIDC client in the same application.
- **Expected result:** Disabled clients retain their configured authentication behavior and trigger no OIDC token grant.
  Only the enabled client uses its selected OIDC mode; existing SOAP results remain unchanged.
- **Priority:** P1.
- **Location:** IT `OidcDisabledTest.java`.

#### T-002: Acquisition supplies a named or default client's access token

- **Covers:** [R-1](spec.md#r-1), [R-2](spec.md#r-2), [R-5](spec.md#r-5), [R-6](spec.md#r-6); [AC-2](spec.md#ac-2),
  [AC-3](spec.md#ac-3), [AC-4](spec.md#ac-4).
- **Level:** integration.
- **Preconditions:** Configure generated `@CXFClient` proxies in `acquire` mode using application properties,
  once without `oidc.client-name` and once with a named client; no authenticated caller is needed.
- **Input / steps:** Make synchronous and asynchronous SOAP calls for both client selections.
  Record the token grant and the outbound SOAP headers.
- **Expected result:** Each call uses the selected client's client-credentials access token as
  `Authorization: Bearer <access_token>` and completes successfully without application token-management interceptors.
- **Priority:** P1.
- **Location:** IT `OidcAcquireTest.java`; APP `OidcClientResource.java`.

#### T-003: Propagation resolves the caller anew through SOAP and REST ingress

- **Covers:** [R-1](spec.md#r-1), [R-3](spec.md#r-3), [R-5](spec.md#r-5), [R-6](spec.md#r-6); [AC-2](spec.md#ac-2),
  [AC-3](spec.md#ac-3).
- **Level:** integration.
- **Preconditions:** Authenticated SOAP and REST endpoints share an injected `propagate` proxy.
  No acquisition/exchange client is needed for propagation.
- **Input / steps:** Invoke each endpoint as A, then B, then A with a replacement access token,
  using both synchronous and asynchronous downstream calls.
- **Expected result:** Each downstream call sends that invocation's authenticated access token exactly,
  with the Bearer scheme; no token grant occurs and no previously observed caller token is reused.
- **Priority:** P1.
- **Location:** IT `OidcPropagationTest.java`; APP `OidcClientResource.java` and `OidcRelayService.java`.

#### T-004: Exchange sends the resulting token rather than the subject token

- **Covers:** [R-1](spec.md#r-1), [R-4](spec.md#r-4), [R-5](spec.md#r-5), [R-6](spec.md#r-6); [AC-2](spec.md#ac-2),
  [AC-3](spec.md#ac-3), [AC-4](spec.md#ac-4).
- **Level:** integration.
- **Preconditions:** Configure `exchange` proxies with default and named RFC 8693 clients.
  The fixture returns an exchanged token distinguishable from the authenticated caller token.
- **Input / steps:** Exercise SOAP and REST ingress with synchronous/asynchronous downstream calls.
  Inspect token-endpoint grant/subject data and downstream Authorization.
- **Expected result:** The selected client performs RFC 8693 exchange for the current caller token,
  and the SOAP request carries `Bearer <exchanged_access_token>`.
  It does not authenticate with the original subject token.
- **Priority:** P1.
- **Location:** IT `OidcExchangeTest.java`; APP `OidcRelayService.java`.

#### T-005: Credential selection uses the authenticated identity and rejects ambiguity

- **Covers:** [R-3](spec.md#r-3), [R-8](spec.md#r-8); [AC-6](spec.md#ac-6).
- **Level:** unit, or the smallest deployment integration fixture if identity selection is framework-bound.
- **Preconditions:** Provide identities with one access-token credential, none, and multiple distinct credentials,
  and an anonymous identity.
- **Input / steps:** Resolve the credential for both caller-dependent modes.
  For the valid identity, also provide a different raw incoming Authorization value or no raw header.
- **Expected result:** The single authenticated credential is selected regardless of the raw HTTP header.
  Anonymous, absent, and ambiguous credentials fail; there is no arbitrary choice among multiple tokens.
- **Priority:** P1.
- **Location:** RT `OidcCredentialSelectionTest.java`, or DT with the same filename if needed.

#### T-006: Unavailable caller credentials prevent downstream dispatch

- **Covers:** [R-3](spec.md#r-3), [R-8](spec.md#r-8), [R-12](spec.md#r-12); [AC-2](spec.md#ac-2), [AC-6](spec.md#ac-6).
- **Level:** integration.
- **Preconditions:** A deployment fixture lets an anonymous request reach the invocation code,
  installs authenticated identities with absent/ambiguous credentials, and can invoke without a request context.
  Warm the shared proxy with a valid caller before each negative scenario.
- **Input / steps:** Invoke `propagate` and `exchange` synchronously and asynchronously in each invalid context.
  For the contextless case use an executor/task without inherited request state.
- **Expected result:** Invocation fails and the SOAP recorder sees no POST for its operation ID.
  A warmed proxy does not fall back to the previous caller's token.
  Assert failure without fixing an unspecified exception class or HTTP mapping; see Q-2.
- **Priority:** P1.
- **Location:** DT `OidcMissingCredentialTest.java`;
  IT `OidcPropagationTest.java` and `OidcExchangeTest.java` cover HTTP-reachable variants.

#### T-007: Invalid modes and incompatible grants cannot create a usable client

- **Covers:** [R-1](spec.md#r-1), [R-5](spec.md#r-5); [AC-7](spec.md#ac-7).
- **Level:** integration.
- **Preconditions:** Separate deployment configurations for an invalid mode value
  and a valid mode paired with an incompatible OIDC grant.
- **Input / steps:** Resolve the injected SOAP proxy, forcing client creation before any operation is sent.
  Use the compatibility matrix resolved in Q-1 to choose incompatible grant pairs.
  Candidate pairs include `exchange` with client credentials and `acquire` with token exchange,
  but their rejection must be confirmed before becoming test expectations.
- **Expected result:** A mode outside the four allowed values is rejected.
  An incompatible grant is rejected on SOAP client creation, not deferred until sending a SOAP operation.
  Unknown client names and blank configuration values need the outcomes in Q-1 before adding exact assertions.
- **Priority:** P1.
- **Location:** DT `OidcConfigurationTest.java`, with separate invalid-configuration fixtures as needed.

#### T-008: Existing HTTP authentication conflicts fail at client creation

- **Covers:** [R-14](spec.md#r-14); [AC-7](spec.md#ac-7), [AC-11](spec.md#ac-11).
- **Level:** integration.
- **Preconditions:** Configure each enabled OIDC mode together with Basic credentials;
  also include Digest as an existing similar authentication scheme.
- **Input / steps:** Force creation of each injected SOAP client without invoking its service.
- **Expected result:** Client creation fails for conflicting HTTP authentication settings.
  No SOAP operation is dispatched; the disabled-mode controls are T-001.
  Do not infer static Bearer or custom-supplier conflict rules until Q-3 is resolved.
- **Priority:** P1.
- **Location:** DT `OidcAuthenticationConflictTest.java`.

#### T-009: OIDC clients use the supported conduit

- **Covers:** [R-6](spec.md#r-6), [R-20](spec.md#r-20); [AC-1](spec.md#ac-1), [AC-7](spec.md#ac-7).
- **Level:** integration.
- **Preconditions:** Explicit per-client Vert.x conduit configuration,
  including a run with URLConnection as global default.
  A separate negative configuration explicitly selects URLConnection for an OIDC client.
- **Input / steps:** Inspect the effective conduit and invoke each enabled mode in the supported configuration.
  Exercise the unsupported configuration once Q-4 defines its rejection behavior.
- **Expected result:** Supported clients use `VertxHttpClientHTTPConduit` and succeed in all modes.
  The spec does not define the unsupported configuration's failure phase or fallback policy;
  its negative assertions remain blocked on Q-4.
- **Priority:** P1.
- **Location:** DT `OidcConduitTest.java`, following existing `ClientConduitFactoryTest`.

### Token lifecycle, isolation, and failures

#### T-010: Valid tokens are reused and expired tokens without refresh are reacquired

- **Covers:** [R-2](spec.md#r-2), [R-4](spec.md#r-4), [R-9](spec.md#r-9); [AC-5](spec.md#ac-5).
- **Level:** integration.
- **Preconditions:** Token responses have controlled lifetimes and no refresh token.
  Configure the applicable Quarkus lifecycle/cache settings for acquisition and exchange.
- **Input / steps:** Call twice while the token is reusable, then again after its configured usable lifetime ends.
  Hold the exchange subject/client/grant tuple fixed and cover named/default client selection.
- **Expected result:** Calls in the reuse window use the reusable token.
  A later call obtains a fresh usable token through the selected grant rather than sending the expired token.
  Cache timing follows the applicable Quarkus settings, whose exact mapping needs Q-5.
- **Priority:** P1.
- **Location:** IT `OidcTokenLifecycleTest.java`.

#### T-011: A refresh-capable lifecycle replaces an expiring token

- **Covers:** [R-9](spec.md#r-9), [R-12](spec.md#r-12); [AC-5](spec.md#ac-5), [AC-8](spec.md#ac-8).
- **Level:** integration.
- **Preconditions:** An applicable selected OIDC client receives an access token and refresh token;
  configure its documented refresh behavior.
- **Input / steps:** Drive calls into the refresh window, record the refresh grant, and return a replacement token.
  Repeat with a failing refresh and no successful alternative acquisition.
- **Expected result:** Subsequent SOAP calls use the replacement access token supplied by Quarkus lifecycle support.
  If no usable token can be supplied, the invocation fails before sending SOAP.
  Exact refresh-failure fallback and applicability to exchange depend on Q-5.
- **Priority:** P1.
- **Location:** IT `OidcTokenLifecycleTest.java`.

#### T-012: Exchange caching separates every required key dimension

- **Covers:** [R-4](spec.md#r-4), [R-9](spec.md#r-9), [R-10](spec.md#r-10); [AC-4](spec.md#ac-4), [AC-5](spec.md#ac-5),
  [AC-12](spec.md#ac-12).
- **Level:** integration.
- **Preconditions:** Enable applicable exchange caching and provide distinguishable tokens for each fixture tuple.
- **Input / steps:** Repeat an identical tuple, then change only the subject token,
  only the selected OIDC client, and only a supported additional grant parameter such as audience or scope.
  Include two different token values with the same subject claim.
- **Expected result:** Reuse is confined to the identical subject-token/client/grant-parameter tuple.
  No changed tuple receives another tuple's exchanged token, including two tokens belonging to the same subject.
  Relevant parameters and their configuration surface need confirmation in Q-5.
- **Priority:** P1.
- **Location:** IT `OidcExchangeIsolationTest.java`.

#### T-013: Concurrent callers never share credentials or exchanged results

- **Covers:** [R-3](spec.md#r-3), [R-4](spec.md#r-4), [R-10](spec.md#r-10); [AC-2](spec.md#ac-2),
  [AC-12](spec.md#ac-12).
- **Level:** integration.
- **Preconditions:** A and B share injected proxies;
  token and SOAP fixtures can hold and release responses independently.
- **Input / steps:** Overlap A/B calls in `propagate` and `exchange`, across SOAP/REST ingress and sync/async calls.
  Reverse token-endpoint completion order, repeat after cache warmup, and interleave a missing-credential call.
- **Expected result:** Every recorded SOAP operation carries its caller's token or the corresponding exchange result.
  Invalid callers still fail; neither worker reuse nor cache hits transfer credentials between invocations.
  No throughput or exact concurrent token-request count is asserted.
- **Priority:** P1.
- **Location:** IT `OidcCallerIsolationTest.java`.

#### T-014: Token-endpoint errors and timeouts fail before SOAP dispatch

- **Covers:** [R-2](spec.md#r-2), [R-4](spec.md#r-4), [R-12](spec.md#r-12), [R-16](spec.md#r-16); [AC-2](spec.md#ac-2),
  [AC-8](spec.md#ac-8).
- **Level:** integration.
- **Preconditions:** Clear reusable tokens or use fresh clients so a grant is required.
  Configure finite endpoint timeout/retry settings and record all SOAP requests.
- **Input / steps:** For acquisition/exchange and sync/async calls, return OAuth rejection,
  HTTP 5xx, malformed JSON, or a response with missing/empty access token;
  also exercise connection refusal and a response delayed beyond the configured timeout.
- **Expected result:** When the selected OIDC client cannot supply a usable token,
  invocation fails with zero SOAP POSTs.
  Observable errors do not expose token values.
  Do not assert an unspecified retry count, exception type, or exact duration; see Q-2 and Q-5.
- **Priority:** P1.
- **Location:** IT `OidcTokenFailureTest.java`.

#### T-015: Authorization failures never replay a SOAP operation

- **Covers:** [R-13](spec.md#r-13); [AC-2](spec.md#ac-2), [AC-3](spec.md#ac-3).
- **Level:** integration.
- **Preconditions:** A stateful SOAP fixture records receipt before returning 401 with a Bearer challenge,
  401 without a challenge, or 403; use all three modes.
- **Input / steps:** Submit one uniquely identified operation through each synchronous/asynchronous client.
  Observe request records after the failure completes.
- **Expected result:** The operation fails and exactly one SOAP POST was received for that operation ID.
  CXF authorization handling and any token refresh do not replay the operation.
  Token-endpoint retries are counted separately from SOAP requests.
- **Priority:** P1.
- **Location:** IT `OidcAuthorizationFailureTest.java`.

### Redirects and secret handling

#### T-016: Origin comparison includes host, port, and scheme

- **Covers:** [R-15](spec.md#r-15), [R-19](spec.md#r-19); [AC-9](spec.md#ac-9), [AC-10](spec.md#ac-10).
- **Level:** unit, or deployment integration if the header decision cannot be tested independently.
- **Preconditions:** Exercise the actual redirect/header decision used by OIDC,
  if an independently callable boundary exists.
- **Input / steps:** Compare a source URI against a different path on the same explicit origin,
  then against targets differing in host only, port only, or scheme only.
- **Expected result:** Same-origin SOAP redirects may resend Bearer credentials;
  each single-component origin change suppresses them.
  Default-port normalization and multi-hop return behavior are reserved for Q-6.
- **Priority:** P2.
- **Location:** RT `OidcRedirectOriginTest.java`, or DT with the same filename if needed.

#### T-017: Actual SOAP redirects retain credentials only within the origin

- **Covers:** [R-15](spec.md#r-15), [R-20](spec.md#r-20); [AC-2](spec.md#ac-2), [AC-3](spec.md#ac-3),
  [AC-9](spec.md#ac-9).
- **Level:** integration.
- **Preconditions:** Redirect following is enabled and existing transport restrictions allow each target.
  Configure a 307 SOAP redirect with a real destination recorder, including trusted HTTPS listeners.
- **Input / steps:** For all modes and sync/async calls, follow a same-origin path redirect,
  then host-only, port-only, and HTTP/HTTPS origin changes.
  Include HTTP-to-HTTPS and HTTPS-to-HTTP scheme changes.
- **Expected result:** The same-origin destination receives the mode's Bearer token and completes the operation.
  Every reached different-origin destination receives no Authorization header.
  Destination authentication failure is acceptable for the latter;
  assert header handling without prescribing destination success.
- **Priority:** P1.
- **Location:** IT `OidcRedirectTest.java` and `OidcTestResource.java`.

#### T-018: Tokens remain masked in messages, diagnostics, and errors

- **Covers:** [R-16](spec.md#r-16); [AC-8](spec.md#ac-8), [AC-9](spec.md#ac-9), [AC-10](spec.md#ac-10).
- **Level:** integration.
- **Preconditions:** Enable CXF logging globally and per client in separate configurations;
  use recognizable synthetic access, subject, exchanged, and refresh token values.
  Capture application logs, emitted diagnostics, and exception cause chains.
- **Input / steps:** Exercise successful calls, grant failures, downstream 401,
  redirects, and protected WSDL loading in the applicable modes.
  Include a controlled token-endpoint error that contains a synthetic token value.
- **Expected result:** Logs confirm that the tested operations were logged but expose none of the token values.
  Any logged token-bearing header is masked, and diagnostics/authentication errors do not reveal tokens.
  Do not require a particular replacement string absent a specification requirement.
- **Priority:** P1.
- **Location:** DT `OidcSensitiveDataTest.java`; IT `OidcLoggingTest.java` for application/native logs.

### WSDL retrieval

#### T-019: WSDL retrieval applies OIDC only when enabled

- **Covers:** [R-17](spec.md#r-17); [AC-10](spec.md#ac-10).
- **Level:** integration.
- **Preconditions:** Fresh clients use a public remote WSDL with `secure-wsdl-access` omitted or false.
  Configure each OIDC mode and provide valid caller credentials for the later SOAP operation where needed.
- **Input / steps:** Trigger runtime WSDL loading and then invoke SOAP.
  Distinguish recorded WSDL GETs from operation POSTs.
- **Expected result:** WSDL requests receive no OIDC Authorization header from the new integration.
  The SOAP operation still uses its configured mode and succeeds.
  Also verify that WSDL loading alone can complete without caller credentials when the gate is disabled.
- **Priority:** P1.
- **Location:** IT `OidcWsdlTest.java`.

#### T-020: Enabled protected WSDL loading authenticates in every mode

- **Covers:** [R-2](spec.md#r-2), [R-3](spec.md#r-3), [R-4](spec.md#r-4), [R-17](spec.md#r-17); [AC-3](spec.md#ac-3),
  [AC-4](spec.md#ac-4), [AC-10](spec.md#ac-10).
- **Level:** integration.
- **Preconditions:** Fresh injected clients enable `secure-wsdl-access` against a protected root WSDL.
  Provide a valid caller for propagation/exchange and named/default clients for acquisition/exchange.
- **Input / steps:** Create the proxy in the required context, load the WSDL, then invoke its SOAP operation.
- **Expected result:** WSDL loading succeeds using the acquired, propagated, or exchanged Bearer token as appropriate.
  The subsequent SOAP operation also authenticates successfully.
  Do not require WSDL GET and SOAP POST to trigger separate grants or identical token values across expiry.
- **Priority:** P1.
- **Location:** IT `OidcWsdlTest.java`.

#### T-021: Protected WSDL loading fails without the required caller token

- **Covers:** [R-8](spec.md#r-8), [R-18](spec.md#r-18); [AC-6](spec.md#ac-6), [AC-10](spec.md#ac-10).
- **Level:** integration.
- **Preconditions:** Fresh `propagate`/`exchange` clients enable secure WSDL access.
  Use anonymous, absent/ambiguous credentials, and no-request-context fixtures.
- **Input / steps:** Trigger WSDL loading before any valid caller has initialized that client.
  Exercise startup/eager creation as the contextless variant where applicable.
- **Expected result:** WSDL loading fails and no SOAP operation can be dispatched through that failed initialization.
  The spec does not define whether an unauthenticated WSDL GET is attempted before failure; see Q-7.
- **Priority:** P1.
- **Location:** DT `OidcWsdlMissingCredentialTest.java`;
  IT `OidcWsdlTest.java` covers request-triggered missing credentials.

#### T-022: WSDL redirects and imports cannot send credentials to another origin

- **Covers:** [R-17](spec.md#r-17), [R-19](spec.md#r-19); [AC-9](spec.md#ac-9), [AC-10](spec.md#ac-10).
- **Level:** integration.
- **Preconditions:** Enable secure WSDL access with valid credentials.
  The root WSDL has valid WSDL/XSD imports, and separate fixtures redirect its retrieval to another origin.
- **Input / steps:** Exercise each mode with host-only, port-only, and HTTP/HTTPS origin changes.
  Use publicly readable target documents so a failed fetch cannot hide header leakage.
- **Expected result:** Reached cross-origin WSDL redirect targets and imported-document servers
  receive no Authorization header.
  Use Q-7 to resolve same-origin import authentication and Q-6 for redirect-chain semantics.
- **Priority:** P1.
- **Location:** IT `OidcWsdlOriginTest.java` and `OidcTestResource.java`.

## Risks

- Local OIDC fixtures can prove grant selection and token routing without reproducing every provider policy.
  Use real Quarkus authentication/token helpers in integration tests; do not replace them with mocked success paths.
- Expiry and concurrent execution can be flaky if controlled only by sleep durations.
  Use recorded requests, completion barriers, configured lifecycle windows, and bounded polling.
- Missing-credential requests rejected by inbound HTTP security never reach CXF and cannot prove [R-8](spec.md#r-8).
  The deployment fixtures must demonstrate that the SOAP invocation itself was attempted and rejected.
- Existing redirect restrictions can reject a destination before its header behavior is exercised.
  Establish reachability and record destination requests, including the port-only origin change.
- WSDL caching and eager initialization can hide the caller context actually used during document retrieval.
  Keep fresh-client missing-context tests separate from already-initialized clients and operation calls.
- A test that only checks successful output can miss a replay or identity leak.
  Operation IDs, request counts, and observed credentials are part of the primary assertions.
- Logs emitted by test fixtures can create false masking failures or disclose synthetic test values unnecessarily.
  Capture application channels explicitly and prove logging is active before asserting token absence.
- JVM deployment fixtures alone cannot prove native behavior.
  Native coverage needs HTTP-driven application scenarios and external fixture observation.
- The Quarkus 4.0 target can change lifecycle APIs/configuration during the stream's development.
  Confirm Q-5 against the implementation's selected version before fixing exact refresh/cache assertions.

## Open Questions

The spec has no Open questions section, so questions are recorded here without editing its requirements.

1. **Q-1 — Configuration and grant matrix (T-007):** Which grants are compatible with each mode beyond
   client credentials for acquisition and RFC 8693 for exchange?
   What are the required outcomes and failure phases for an unknown OIDC client name,
   blank client name, and empty mode value?
   When `oidc.client-name` is set in `propagate` or `disabled`, is it ignored or rejected as unused configuration?
2. **Q-2 — Failure contract (T-006, T-014):** Are particular exception types or actionable message fields required
   for missing credentials, token acquisition failure, and timeout?
   The plan can assert failure and zero SOAP dispatch without choosing an exception or REST/SOAP error mapping.
3. **Q-3 — Authentication conflicts (T-008):** Does "Basic or similar authentication" include configured static Bearer,
   an empty/default auth block, a custom `HttpAuthSupplier`, or an explicitly supplied Authorization header?
   Which combinations must fail at client creation?
4. **Q-4 — Unsupported conduit (T-009):** Must OIDC with a non-Vert.x conduit fail at client creation,
   fail at configuration/augmentation, or select Vert.x automatically?
   The support restriction alone does not define an observable negative result.
5. **Q-5 — Lifecycle configuration and exchange keys (T-010–T-014):** Which documented Quarkus 4.0 settings
   control the integration's reuse, refresh, reacquisition, timeout, and exchange caching?
   Which grant parameters form the exchange cache key and how can the application configure them?
   Is refresh supported for exchanged tokens, and what fallback follows refresh rejection?
   Resolve these before asserting exact grant counts or boundary timing;
   no guarantee of coalescing concurrent token requests is currently specified.
6. **Q-6 — Redirect edge cases (T-016, T-017, T-022):** How are implicit/default ports normalized,
   and can credentials be restored after a chain leaves the original origin and later returns?
   Define the origin against which each hop is checked before adding those boundary assertions.
7. **Q-7 — WSDL details (T-020–T-022):** Are same-origin WSDL/XSD imports authenticated when secure access is enabled,
   and must missing caller credentials fail before even the initial WSDL GET?
   Which behavior is required for eager client creation when a caller-dependent WSDL token cannot yet exist?
   Failure is specified, but its exact initialization phase and recovery on a later valid request are not.
8. **Q-8 — Optional refresh on unauthorized (T-024):** Will such an option be offered in this change?
   If so, define its name, default, modes, and qualifying responses.
   If not, mark T-024 not applicable; T-015 still proves the mandatory no-replay rule.
