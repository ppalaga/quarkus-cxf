# Implementation Plan: Quarkus OIDC Client integration for SOAP clients

## Summary

Add `quarkus-cxf-oidc` with configuration-driven acquisition, propagation,
and RFC 8693 exchange for injected SOAP clients.
Reuse Quarkus token lifecycle support through an extension-owned adapter,
and add narrowly scoped core hooks for invocation context, transport authentication, and WSDL loading.
The 14 tasks below retain the existing requirement IDs and test cases,
with explicit dependencies for unresolved behavior and the exchange-cache gap in the currently selected Quarkus version.

## Scope

In scope:

- [R-1](spec.md#r-1) through [R-21](spec.md#r-21) and [AC-1](spec.md#ac-1) through [AC-13](spec.md#ac-13), including generated interfaces without OIDC annotations,
  default/named clients, synchronous/asynchronous calls, SOAP/REST ingress, and JVM/native execution.
- Per-invocation security-context credentials, Quarkus-managed token lifecycle, isolated exchange results,
  failure before SOAP dispatch, no operation replay, origin checks, and masking.
- Runtime WSDL retrieval behind `secure-wsdl-access`, including redirects and imports.
- Integration-test examples and documentation of exchange caching's effect on revocation detection.
- Compatibility with existing clients when OIDC is absent or disabled.

Out of scope:

- `@OidcClientFilter`, `@AccessToken`, programmatic JAX-WS clients, JWT-bearer exchange, and other HTTP conduits.
- A new token lifecycle implementation, automatic SOAP replay, or new revocation guarantees.
- Unspecified performance targets, migration procedures, backports, or broad changes to existing authentication.
- Implementing the feature or changing test code in this planning task.

The spec's original scenarios and design-context section supply the use cases;
there is no separate use-case assessment or migration procedure.
Quarkus 4.0 and disabled-mode compatibility are the stated compatibility boundaries.

Transport details that affect the approach:

- `CxfClientProducer` constructs the client-specific conduit factory after invoking client customizers.
  It temporarily installs that factory on the shared bus during `factory.create()` for WSDL loading,
  with a comment assuming no concurrent access.
  An OIDC provider or caller token must not be exposed through an unsafe shared-bus swap.
- WSDL GET messages do not pass through ordinary SOAP operation interceptors.
  A SOAP-only outbound interceptor cannot satisfy [R-17](spec.md#r-17) through [R-19](spec.md#r-19).
- `RequestBodyHandler` treats 401/407 as possible authorization retransmits.
  `possibleRetransmit` also becomes true when redirects are enabled,
  so merely supplying a non-caching authentication supplier does not establish [R-13](spec.md#r-13).
- `redirect()` calls `retransmit()` with an identity options customizer;
  `retransmit()` copies the original `RequestOptions`, including headers.
  Existing `checkAllowedRedirectUri()` checks optional host/scheme restrictions, not the complete token-origin rule.
- CXF `HTTPConduit.prepare()` calls its synchronous authentication supplier before creating the output stream.
  Reusing that API as a blocking token-fetch callback would constrain async execution.
  A request-scoped asynchronous authentication hook is the proposed alternative.

### Quarkus dependency findings

The source archive for `io.quarkus:quarkus-oidc-client:4.0.0.Beta1` was inspected directly,
including `OidcClients`, `runtime/OidcClientsConfig`, `runtime/AbstractTokensProducer`,
`runtime/TokensHelper`, `runtime/TokenProviderImpl`, and `runtime/OidcClientImpl`.
These paths are archive entries under `io/quarkus/oidc/client`, not files in this repository.

- `OidcClients.getClient()` and `getClient(String)` select default/named clients.
  `OidcClientsConfig.getDefaultClient()` resolves default configuration;
  `OidcClientConfig.Grant.Type.CLIENT` and `EXCHANGE` represent the two required grant families.
- `AbstractTokensProducer` and `TokensHelper` already handle reuse, expiry, refresh, and reacquisition.
  `refreshInterval()` explicitly applies to producer/filter integration
  rather than direct `OidcClient.getTokens()` calls.
  An adapter must preserve the applicable configuration behavior, not just call the raw grant API.
- **Exchange reuse is not safe through one shared Beta1 helper.**
  `TokensHelper` holds one `tokenRequestState`, and `TokenProviderImpl.getAccessToken(Map)` delegates to that helper.
  The additional-parameter map does not partition the cached or in-flight state.
  This contradicts the spec's contextual observation about parameter-isolated caching
  for this selected dependency version.
  [Q-9](#q-9) blocks the final exchange-cache implementation; it does not change [R-9](spec.md#r-9) or [R-10](spec.md#r-10).
- `OidcClientImpl.emitGrantTokens()` logs a failed token response body at DEBUG
  and embeds it in `OidcClientException`.
  Sanitizing a later CXF exception cannot remove an earlier dependency log entry.
  [Q-10](#q-10) identifies the required redaction integration or upstream prerequisite.

## Proposed Approach

The design choices below are proposals; they do not add configuration or behavior requirements to the spec.

### Extension ownership and client activation

Create `extensions/oidc` with runtime/deployment modules and the `quarkus-cxf-oidc` runtime artifact.
Follow the OpenTelemetry extension's separate runtime config mapping,
using `quarkus.cxf.client."client-name".oidc.mode` and `.client-name` without adding OIDC dependencies to core.
Reuse the resolved SOAP configuration key rather than independently interpreting `@CXFClient` injection points.

An OIDC `ClientFactoryCustomizer` validates the selected mode, grant, existing authentication, and effective conduit
before the proxy is created.
It installs an immutable provider/configuration reference through factory properties for enabled clients.
An absent group or `disabled` installs no authentication behavior.
The provider reference may be shared; an invocation's credential or token must not live in shared proxy properties,
`AuthorizationPolicy`, or mutable client metadata.

Use `quarkus-oidc-client` and the minimal security/access-token API dependencies identified in [I-001](#i-001).
The integration-test application needs inbound `quarkus-oidc` authentication for SOAP/REST ingress.
Do not require an inbound identity-provider configuration merely to use acquisition.
Runtime/deployment dependency pairs and native registration follow existing extension patterns.

### Invocation and HTTP request data flow

1. Resolve the configured provider when an injected SOAP operation is invoked.
   For propagation/exchange, obtain exactly one access-token credential from the authenticated security context.
   Capture the invocation's credential before worker dispatch; account for deferred identity resolution without blocking
   an event-loop thread or retaining a request-scoped bean after its context terminates.
2. Transfer the immutable invocation state to that operation's CXF message/exchange.
   Extend the proxy/invocation boundary only as needed for this transfer;
   exclude `Object`, `BindingProvider`, and close/control methods from SOAP authentication.
   Any scoped transfer mechanism must restore its previous state on success, failure, and nested calls.
3. Let the OIDC adapter return an asynchronous token result.
   A proposed core contract uses `CompletionStage` and an extension-neutral request context,
   so core does not import OIDC types.
   Propagation returns the captured token; acquisition/exchange delegate lifecycle work to Quarkus.
4. Gate the Vert.x request creation on the token result, before any SOAP bytes are dispatched.
   Integrate before `setProtocolHeaders()`/`client.request()` in `RequestBodyHandler`,
   with the provider/state already attached to the message.
   Token failure must wake blocked writers and complete the existing response/callback path exactly once.
   Preserve existing synchronous worker behavior and async callback semantics.
5. Apply one Bearer header to the current request, with origin and no-replay metadata kept separately from its value.
   Re-evaluate header eligibility on redirect instead of blindly copying it.
   Never enter authorization replay for an OIDC operation after downstream authorization failure.

### Lifecycle, WSDL, and compatibility boundaries

Use existing Quarkus lifecycle behavior for acquisition and require a verified isolation mechanism for exchange.
The logical exchange identity is the selected OIDC client, exact subject-token value, and relevant grant parameters.
Do not substitute the caller's subject claim for its token value.
Do not share one Beta1 `TokensHelper` across different tuples or replace lifecycle behavior with a new CXF cache.
Prefer a Quarkus 4.0 dependency with the required capability; if unavailable,
[Q-9](#q-9) requires an explicit supported adaptation/upstream solution before completing exchange reuse.
Owned adapter state must be released with its client/application, without closing Quarkus-managed clients prematurely.

For WSDL, carry the client-specific provider, root document origin, and caller snapshot into document resolution.
The resolver must obtain the correct factory without exposing a caller-specific factory globally on the bus.
Prefer a scoped creation context consumed by the resolver, restored in `finally`,
over serializing network I/O behind a shared lock.
Apply the secure-WSDL gate before token resolution, and preserve classpath/file loading.
Authenticate the root document only when enabled, and strip credentials from cross-origin imports/redirects.
Same-origin imports, cached-definition behavior, and startup failure details remain [Q-7](#q-7).

Extend the existing logging-feature setup to mask Authorization for enabled OIDC clients,
preserving existing user masking configuration.
Handle token-endpoint errors without retaining secret-bearing cause chains or response bodies in diagnostics.
Dependency logging must be addressed before claiming full masking compliance.

These changes require no migration for existing clients: absent/disabled OIDC keeps the existing path,
and Basic/Digest/static Bearer behavior remains covered by regression tests.
The proposed default is to omit a new refresh-on-unauthorized option in this change;
[Q-8](#q-8) must confirm whether [T-024] is applicable.
The no-replay rule is mandatory either way.

## Risks

- The selected Quarkus helper cannot safely cache exchange results across callers without additional capability.
  Make [Q-9](#q-9) a hard dependency of exchange reuse and retain both cached-state and in-flight isolation tests.
- Putting tokens in a shared proxy, conduit authorization policy, bus extension, or long-lived request-context object
  can transfer identity between callers.
  Limit shared state to provider/configuration references and test concurrent invocation and client creation separately.
- Suspending token acquisition within the streaming request path can strand writers or double-complete callbacks.
  Reuse existing failure signaling and cover delayed grants, endpoint failure, and worker-dispatch timeout.
- A raw token-endpoint error may be logged before the extension sees the failure.
  Verify the selected dependency/filter path, not just the CXF wrapper, before accepting [T-018].
- WSDL manager caching and separate schema resolution may bypass an operation-only security hook.
  Follow root WSDL, imported WSDL, and XSD fetches through their actual resolver paths and resolve [Q-7](#q-7).
- Broad changes to conduit authentication can break Digest retransmission or Basic WSDL access.
  Keep OIDC request behavior explicitly scoped and run the existing focused regressions.
- New extension dependencies or beans can change startup in acquire-only or disabled applications.
  Verify the dependency graph and disabled-mode startup without imposing inbound provider configuration.
- Native tests cannot inspect in-process JVM fixtures or injected test beans.
  Design observations through HTTP/log files from [I-003](#i-003) and exercise all modes in [T-026].

## Open Questions

The spec has no Open questions section, so this plan records issues here without changing its requirements.
[Q-1](#q-1) through [Q-8](#q-8) carry forward the [test-plan questions](test-plan.md#open-questions);
[Q-9](#q-9) and [Q-10](#q-10) capture additional source-level findings.

### Blocking behavior and dependency questions

- <a id="q-1"></a>**Q-1 — Grant/configuration matrix:** Confirm allowed grants beyond the two requested families,
  unknown/blank client-name handling, empty mode values, and unused selection in disabled/propagate modes.
  Blocks the affected [I-004](#i-004)/[T-007] cases; module/config scaffolding and positive paths can proceed.
- <a id="q-3"></a>**Q-3 — Authentication conflict boundary:** Does the creation-time conflict include static Bearer,
  custom suppliers, manually supplied Authorization, or an empty/default auth block?
  Blocks those additional [I-004](#i-004) cases; specified Basic conflicts can proceed.
- <a id="q-4"></a>**Q-4 — Unsupported conduit:** Should an explicitly incompatible conduit fail at creation,
  fail at augmentation, or be replaced automatically?
  Proposal: fail at client creation rather than silently change the user's transport.
  This is a proposed policy, not a requirement; resolve it before finalizing [I-004](#i-004)/[T-009].
- <a id="q-5"></a>**Q-5 — Lifecycle configuration:** Which existing Quarkus settings apply to each mode,
  including early acquisition, periodic refresh, refresh rejection, timeout, and additional exchange parameters?
  Blocks final adapter/configuration assertions in [I-006](#i-006)/[I-007](#i-007) and the corresponding documentation in [I-013](#i-013).
  Caller-dependent exchange cannot obtain a subject token during contextless startup.
- <a id="q-6"></a>**Q-6 — Redirect edges:** Define default-port normalization and whether credentials can return
  after a redirect chain leaves and re-enters the initial origin.
  Blocks those [I-010](#i-010)/[I-011](#i-011) edge cases; explicit same/different-origin cases can proceed.
- <a id="q-7"></a>**Q-7 — WSDL details:** Define same-origin import authentication, missing-token failure phase,
  eager initialization/recovery, and whether cached definitions require a new caller-availability check.
  The cache question extends the test-plan question: can a shared URL's cached definition be reused across identities
  when a server could serve different authenticated documents?
  Blocks those [I-011](#i-011) choices; the secure-access gate, cold missing-token failure, and cross-origin suppression are specified.
- <a id="q-9"></a>**Q-9 — Exchange reuse on the target version:** Which supported Quarkus 4.0 API/version
  supplies tuple-isolated exchange lifecycle state, given Beta1's single-state helper?
  Prefer an upstream capability consistent with [R-9](spec.md#r-9)/[R-10](spec.md#r-10);
  if it does not exist, identify the required upstream change or explicitly reviewed adaptation.
  A shared helper is unsafe and disabling reuse silently would not fulfill the planned lifecycle coverage.
  Blocks completion of [I-007](#i-007), exchange subsets of [I-008](#i-008)/[I-011](#i-011), and final [I-013](#i-013)/[I-014](#i-014) acceptance.
- <a id="q-10"></a>**Q-10 — Dependency error redaction:** Can a supported client-scoped response-filter mechanism
  redact failed response bodies before Beta1 logs them, without corrupting successful token responses,
  or is an upstream change necessary?
  Verify scope and callback timing rather than assuming interception of the exception is enough.
  Blocks complete [I-012](#i-012)/[T-018] coverage; ordinary CXF header masking can proceed independently.

### Non-blocking assumptions and conditional scope

- <a id="q-2"></a>**Q-2 — Error shape:** Exact exception classes and REST/SOAP mappings are unspecified.
  [I-005](#i-005)/[I-006](#i-006)/[I-008](#i-008) can assert failure before SOAP dispatch and sanitized diagnostics;
  specify extra error fields only if needed, without assuming them in the tests.
- <a id="q-8"></a>**Q-8 — Refresh on unauthorized:** The spec does not require adding this option.
  Proposed scope is to omit it and mark [T-024] not applicable; confirm this before closing [I-009](#i-009)/[I-013](#i-013).
  If it is included, define its configuration, modes, and qualifying responses
  and keep current-operation replay disabled.
- The new filenames and extension-neutral hook design are proposals to verify during implementation,
  not additional public configuration or supported-client promises.
  Keep helper APIs internal where possible and use existing framework dependencies.
- Existing token caching delays detection of changes at the issuer according to the actual selected lifecycle behavior.
  Documentation must describe the confirmed effect rather than infer a new revocation guarantee.
