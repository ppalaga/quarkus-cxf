[[client-oidc]]
== OIDC authentication for SOAP clients

Add `io.quarkiverse.cxf:quarkus-cxf-oidc` to use Quarkus OIDC Client for outbound SOAP authentication.
The extension supports injected `@CXFClient` proxies using `VertxHttpClientHTTPConduitFactory`,
including generated synchronous and asynchronous interfaces, in JVM and native applications.
It does not add authentication to programmatic JAX-WS clients.
Without `oidc.mode`, or with `oidc.mode = disabled`, existing authentication remains unchanged.

The following examples are included from the OIDC integration tests.
Their local provider and SOAP recorder replace `${oidc.fixture.http}` at test startup and enable the named OIDC clients.
In your application, use your provider's token endpoint, client credentials, generated service interface, and SOAP URL.
Acquisition requires `quarkus-oidc-client` configuration,
but does not require an inbound OIDC provider or caller identity.

=== Token lifecycle and revocation

Quarkus owns token reuse, expiry checks, refresh, reacquisition, connection timeouts, and token-endpoint retries.
Acquisition uses its token producer, including `early-tokens-acquisition` and `refresh-interval` where configured.
Exchange uses its parameter-keyed `TokensHelper` cache and is lazy because a subject token is required.
For exchange, early acquisition and background `refresh-interval` are not applied;
refresh or reacquisition takes place during an invocation with that caller's parameters.

The applicable settings include `refresh-token-time-skew`, `access-token-expiry-skew`,
`token-cache-max-size`, `connection-timeout`, and `connection-retry-count` under the selected `quarkus.oidc-client`.
Exchange results and outstanding requests are separated by selected client and the exact subject-token value,
including two different tokens with the same subject claim, and by additional grant parameters.
Configured audience, scope, and grant options belong to the selected OIDC client.
The SOAP configuration does not add an API for per-invocation audience or scope overrides.

Reusing an exchanged token does not contact the issuer to revalidate its subject token on every SOAP call.
Revoking the subject token may therefore not be detected until a later exchange;
the downstream service may enforce its own validation of the exchanged token.
Setting `token-cache-max-size = 0` disables reuse for parameterized exchanges,
but does not create any additional revocation guarantee.

Token-supply failures prevent SOAP dispatch.
A downstream 401 or 403 fails the operation without automatic replay.
This extension does not provide a refresh-on-unauthorized option.
Do not configure Basic, Digest, or static Bearer authentication alongside an enabled OIDC mode.
A non-Vert.x conduit is rejected at client creation rather than silently replaced.

=== Redirects and WSDL access

SOAP redirects retain the Bearer credential only within the same origin: scheme, host, and effective port.
Default HTTP/HTTPS ports are normalized.
Once a redirect leaves the original origin, credentials remain suppressed for the rest of that redirect chain.
Existing redirect enablement and limits still apply.
Authorization values are masked in CXF logging and token-provider errors are sanitized.

Remote WSDL loading uses OIDC only when `quarkus.cxf.client."client-name".secure-wsdl-access = true`.
When enabled, propagation and exchange require a caller during client creation,
so eager or contextless creation of such a client fails.
Root documents and same-origin imports can authenticate;
cross-origin imports and redirect targets receive no credential.
Authenticated WSDL definitions are loaded separately for each proxy creation
rather than shared across caller identities.
With secure WSDL access disabled, fetching a public WSDL does not require a caller,
but subsequent caller-dependent SOAP operations still do.

For a production service, set `quarkus.oidc.auth-server-url` to your provider's realm URL
and configure your own client ID and credentials.

Apply security annotations to the service implementation methods:

.HelloServiceImpl.java
[source,java]
----
include::example$oidc/HelloServiceImpl.java[]
----

* `hello`: no security annotation; allows anonymous access in this configuration.
* `hallo`: `@PermitAll` allows anonymous access.
* `ciao`: `@RolesAllowed("italian")` requires an authenticated user with the `italian` role.
* `hoi`: `@Authenticated` requires authentication, regardless of the user's roles.

Clients send access tokens in the HTTP `Authorization: Bearer <token>` header.
Calls requiring authentication return HTTP 401 when no valid token is supplied;
authenticated callers lacking the required role receive HTTP 403.
